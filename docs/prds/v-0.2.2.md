# TradingZero — PRD v-0.2.2

**Version:** 0.2.2
**Status:** Draft
**Date:** 2026-05-14

---

## Problem Statement

Sebagai trainer TradingZero, saya ingin frontend direkonstruksi dari dashboard web awal menjadi Live View yang benar-benar nyaman untuk memantau Run aktif. Web app v0.2.1 sudah menggantikan TUI dan menyediakan kontrol training, metrik, histori, error, dan konfigurasi. Namun layout masih terasa seperti semua panel ditumpuk dalam satu halaman, chart belum menjadi pusat pengalaman, status Live Stream mudah disalahartikan, dan state kosong belum cukup membantu ketika sistem disconnected, idle, atau sedang menunggu data pertama.

Masalah utama dari perspektif pengguna: saat memantau Run live, saya harus cepat tahu apakah Run sehat, apakah Live Stream tersambung, apa aksi terakhir agent, bagaimana price/action bergerak, dan apa yang bisa saya lakukan berikutnya. Jika chart blank atau layout sulit discan, saya tidak bisa membedakan antara “belum ada Run”, “WebSocket mati”, “Run jalan tapi event belum masuk”, atau “frontend sedang gagal render data”.

---

## Solution

TradingZero akan membangun ulang frontend menjadi dashboard live-monitoring dengan struktur informasi yang jelas, visual dominan, dan domain language yang konsisten.

Solusi dari perspektif pengguna:

1. Default route menjadi Live View untuk memantau Run aktif.
2. Price chart menjadi hero utama, besar, dan selalu punya state visual walau belum ada data.
3. Side nav memisahkan Live View dari Config, Runs, dan Errors sehingga halaman utama tidak penuh fitur sekunder.
4. KPI strip menampilkan Sharpe, Best Sharpe, Balance, PnL, Win Rate, dan Progress secara cepat.
5. Panel Last Action, Run Controls, Action Distribution, dan Stream Health berada di sekitar chart untuk monitoring cepat.
6. Live Stream state dipisahkan dari Run lifecycle state supaya pengguna paham beda antara WebSocket connection dan status training.
7. Idle state dibuat eksplisit: Disconnected, Idle, dan Waiting.
8. Theme menggunakan dark-only neutral trading dashboard dengan teal accent `#2ee6b8`.
9. UI foundation memakai Tailwind v4 + shadcn/ui supaya komponen konsisten dan mudah dikembangkan.
10. Chart stack dikonsolidasikan ke Lightweight Charts untuk trading-platform feel.
11. Frontend tetap kompatibel dengan backend v0.2.1 dan tidak membutuhkan schema/API baru untuk Phase 1.
12. Keputusan arsitektur ADR tetap dihormati: `training_update` tetap dipakai untuk KPI, sedangkan `step_batch` dan `run_steps` menjadi Phase 2 untuk per-Step chart live yang lebih akurat.

## Implementation Decisions

- v0.2.2 is a frontend reconstruction PRD, not a backend streaming/storage PRD.
- Default product surface is Live View, optimized for monitoring a currently active Run.
- Live View uses domain terms from the project glossary: Run, Generation, Episode, Step, Action, Last Action, Live Stream, Training update, Step batch, and Rolling window.
- Layout model: side nav + full Live View.
- Visual hierarchy: price chart hero first, KPI strip second, live context panels third.
- Theme model: dark-only neutral trading interface with teal accent `#2ee6b8`.
- UI foundation: Tailwind v4 + shadcn/ui.
- Routing: React Router v7-style route architecture with `/` for Live View and `/config` for Config page in Phase 1.
- Navigation reserves future surfaces for Runs and Errors, but full implementation of those pages is deferred unless already present.
- Current backend REST endpoints remain unchanged.
- Current WebSocket endpoint remains unchanged.
- Current `training_update` event shape remains unchanged and continues to drive KPI strip, Sharpe trajectory, action distribution, progress, and Last Action.
- ADR-0001 is respected: future per-Step chart updates use `step_batch` on the same Live Stream, while `training_update` remains per-Generation.
- ADR-0002 is respected: future per-Step history persists in `run_steps`, but no schema change is part of v0.2.2 Phase 1.
- Rolling window semantics are used for chart UX: live chart focuses on recent activity rather than becoming an infinite historical browser.
- The Live View must represent three explicit empty/edge states: Disconnected, Idle, and Waiting.
- Disconnected means Live Stream is not connected and should not be conflated with Run state.
- Idle means no active Run is currently training.
- Waiting means Run is active but first live event for display has not arrived yet.
- Chart must never be blank without explanation.
- Chart stack direction: consolidate toward Lightweight Charts only for market/trading visualization.
- ECharts is not the preferred long-term chart stack for this dashboard unless a specific analytics surface later justifies it.
- Config editing moves to a dedicated Config page grouped by backend configuration domains: Data, Env, Agent, Self-play.
- Optional quick-edit Sheet may expose only a small subset of frequently changed settings and must not duplicate full config form complexity.
- Existing run controls remain available through the Live View and preserve current start/stop/retry semantics.
- Existing test IDs for primary controls should be preserved to reduce test churn.
- Deep module strategy:
  - API Client module: encapsulates HTTP requests and response parsing behind stable functions.
  - Run Queries module: encapsulates React Query keys, polling, mutations, and invalidation rules.
  - Live Stream module: owns WebSocket connection state and event handling interface.
  - Chart Adapter module: converts Training update and future Step batch data into chart-ready series and markers.
  - Live View State module: derives UI state such as Disconnected, Idle, Waiting, Running, Done, and Error from Run status plus Live Stream status.
  - Formatting module: centralizes USD, percent, signed PnL, and status display formatting.
  - App Shell module: owns side nav, route outlet, and global dashboard frame.
  - Config Form module: owns grouped config form state, validation, dirty state, and save behavior.
- Deep modules should expose small, testable interfaces and hide incidental UI/library details.
- No auth, multi-user, or deployment behavior is introduced.

## Testing Decisions

- Good tests validate external behavior from user or API perspective, not incidental component structure, CSS class names, private helper calls, or implementation-specific hook internals.
- Tests should assert what user can see or what public module interface returns.
- Live View tests should verify all user-visible state outcomes: Disconnected, Idle, Waiting, Running, Done, and Error when applicable.
- Run control tests should verify Start, Stop, and Retry controls remain reachable and wired to existing behavior.
- API Client tests should verify request paths, methods, and response handling at module boundary if the module contains non-trivial parsing or error normalization.
- Run Queries tests should focus on query/mutation behavior visible at page level unless invalidation logic becomes complex enough to test directly.
- Live Stream tests should verify connection state and event filtering behavior through its public hook/module interface.
- Chart Adapter tests should verify stable conversion from domain data to chart series/markers because it is a deep module with high logic-to-interface ratio.
- Live View State tests should verify derived states from combinations of Run state and Live Stream connection because this prevents ambiguous blank dashboard regressions.
- Formatting tests should continue covering USD, percent, and signed PnL formatting because financial display accuracy matters.
- Config Form tests should verify grouped fields render, existing active config data populates the form, and Save behavior calls the existing config endpoint.
- App Shell tests should verify route navigation renders Live View and Config page without depending on layout internals.
- End-to-end smoke test should cover the operator golden path: open Live View, see stream status, start Run, observe Running/Stopping/Done state, stop Run.
- Browser verification is required for frontend implementation because chart layout, side nav, and visual states cannot be fully trusted from unit tests alone.
- Prior art in current codebase:
  - Existing React/Vitest test validates dashboard header, KPI labels, and start/stop controls.
  - Existing Playwright smoke test validates open dashboard, stream status visibility, start flow, and stop flow.
  - Existing backend WebSocket tests validate runtime dependency and publish path; v0.2.2 should not weaken those guarantees.

## Out of Scope

- Backend schema changes.
- `run_steps` table implementation.
- `step_batch` event implementation.
- New REST endpoints.
- Reworking trainer loop, reward logic, PPO behavior, or checkpoint mechanics.
- Multi-run scheduler.
- Multi-user accounts.
- Authentication or authorization.
- Light theme or theme toggle.
- Full historical replay for `/runs/:id`.
- Global Errors page redesign beyond navigation placeholder or existing behavior.
- Full Runs page redesign beyond navigation placeholder or existing behavior.
- Cloud deployment, hosting, or CI/CD changes.
- Advanced chart decimation or historical query optimization.
- Replacing backend persistence strategy.

## Further Notes

- v0.2.2 builds on v0.2.1, which already introduced web dashboard, FastAPI backend, WebSocket Live Stream, run lifecycle APIs, persisted run/error/config state, and frontend tests.
- This PRD intentionally keeps frontend reconstruction independent from backend per-Step streaming so the UI frame can ship before high-volume Step data work.
- The grill decision was to prefer a trading-platform feel over generic admin dashboard feel.
- The user preference from grill: recommendations should be explicit, language should stay simple, and Live View should optimize for monitoring an active Run.
- If Phase 1 succeeds, Phase 2 should implement `step_batch` and `run_steps` so the price chart can move from per-Generation placeholders toward true per-Step candle/action rendering.
